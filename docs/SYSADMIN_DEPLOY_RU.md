# Инструкция системному администратору: деплой IvaMaris TDO

Актуально на 2026-06-17 (ветка `main`, коммит `ab91599`).
Документ описывает полный деплой/обновление и **новые переменные окружения**,
которые надо добавить для модулей **FEED** (AI-поиск) и **Vendors** (письма
подрядчикам + ссылки-приглашения).

> ⚠️ **Если на проде ошибки `column feed_files.lang does not exist`,
> «No Access-Control-Allow-Origin» при загрузке FEED, или письма падают с
> `DH_KEY_TOO_SMALL` — см. раздел 8 «Разбор инцидента 2026-06-17».**
> Большинство чинится простым `git pull` + пересборкой (авто-миграция БД
> теперь встроена).

---

## 1. Что нового в этом релизе

**FEED (документация стадии FEED):**
- Загрузка с окном прогресса (файлы обрабатываются по одному).
- Дедупликация: одинаковый по содержимому файл не загружается повторно
  (даже под другим именем).
- Главными версиями считаются только PDF (RU/EN/двуязычный); не-PDF (docx/xls)
  помечаются «ред.» — редактируемые исходники.
- Класс 1 без полного комплекта (только одна языковая версия) подсвечивается
  красным; счётчики неполных документов по дисциплинам.
- Поиск исправлен (корректно ищет по кириллице, выдаёт только релевантные
  источники). AI-ответ помечается как «ориентировочный».
- AI-поиск (опционально) через OpenAI-совместимый API; вкл/выкл в админке,
  **по умолчанию выключен**.

**Vendors (закупки):**
- Письмо-приглашение и код доступа отправляются на email подрядчика через
  корпоративный SMTP.
- Ссылка-приглашение автоматически использует адрес, с которого открыт сайт
  (или `PUBLIC_BASE_URL`) — больше не «прибита» к `localhost`.
- В интерфейсе видно, реально ли ушло письмо (или его надо передать вручную).

---

## 2. Предварительные условия

- Docker Engine + Docker Compose plugin на сервере.
- Открыты порты:
  - `3000/tcp` — frontend,
  - `8000/tcp` — backend API.
- Порт `5432` (Postgres) наружу **не** публикуется.
- Сервер доступен пользователям по IP/домену в нужной сети (LAN или интернет).

## 3. Переменные окружения (.env)

Все переменные задаются в файле `.env` в корне проекта (рядом с
`docker-compose.yml`). За образец взять `.env.example`. **`.env` в git не
коммитится** — секреты только на сервере.

### 3.1. Базовые (обязательно)

```dotenv
# База данных
POSTGRES_USER=tdo_app
POSTGRES_PASSWORD=<длинный_случайный_пароль_32+>
POSTGRES_DB=tdms
DATABASE_URL=postgresql+psycopg://tdo_app:<тот_же_пароль>@db:5432/tdms

# Безопасность
SECRET_KEY=<случайный_секрет_64+>

# Первый администратор (создаётся при первом запуске)
FIRST_ADMIN_EMAIL=admin@ivamaris.io
FIRST_ADMIN_PASSWORD=<надёжный_пароль_админа>
MAIN_ADMIN_EMAIL=admin@ivamaris.io
SEED_DEMO_USERS=false

# MinIO
MINIO_ROOT_USER=tdo_minio
MINIO_ROOT_PASSWORD=<пароль_minio_32+>
```

### 3.2. Сетевые — frontend ↔ backend (важно для LAN/прода)

По умолчанию фронт обращается к API по `http://localhost:8000` — это работает
только если пользователь открывает сайт на самом сервере. Для доступа по
IP/домену укажите реальный адрес API и разрешите его в CORS:

```dotenv
# Адрес backend, к которому обращается браузер пользователя.
# Пример для LAN: http://192.168.10.5:8000   Для прода: https://api.tdo.company.ru
VITE_API_URL=http://<IP_или_домен_сервера>:8000

# Разрешённые источники (origin'ы фронта) для CORS — JSON-массив.
# Должен содержать URL, по которому пользователи открывают сайт.
CORS_ORIGINS=["http://<IP_или_домен_сервера>:3000"]
```

> ⚠️ `VITE_API_URL` встраивается в сборку фронта — после его изменения
> фронтенд нужно **пересобрать** (`docker compose build frontend`).

### 3.3. НОВОЕ — Vendors: SMTP + ссылки подрядчикам

Без SMTP письма подрядчикам **не отправляются** (код/ссылка только пишутся в
лог backend). Чтобы письма уходили с корпоративной почты:

```dotenv
SMTP_HOST=mail.company.ru          # SMTP-сервер корпоративной почты
SMTP_PORT=587                       # 587 (STARTTLS) или 465 (SSL)
SMTP_USER=robot@company.ru          # логин ящика-отправителя
SMTP_PASSWORD=<пароль_ящика>        # пароль/пароль приложения
SMTP_FROM=robot@company.ru          # адрес в поле «От кого»
SMTP_USE_TLS=true                   # true для 587/STARTTLS

# Базовый URL, по которому подрядчик откроет ссылку из письма.
# ОБЯЗАТЕЛЬНО для внешних подрядчиков: укажите адрес, доступный ИМ
# (публичный домен или IP, видимый подрядчику). Если оставить localhost,
# система подставит адрес, с которого админ создавал приглашение.
PUBLIC_BASE_URL=https://tdo.company.ru
```

> Для внешних подрядчиков `PUBLIC_BASE_URL` должен быть **публично
> доступным** адресом — ссылка генерируется в момент создания приглашения и
> уходит в письмо. LAN-IP подрядчик из интернета не откроет.

### 3.4. НОВОЕ — FEED: AI-поиск (опционально)

Без этих переменных FEED работает на обычном полнотекстовом поиске. Для
«умного» поиска нейросетью — OpenAI-совместимый провайдер:

```dotenv
# Вариант OpenRouter (есть бесплатные модели):
AI_API_BASE_URL=https://openrouter.ai/api/v1
AI_API_KEY=<ключ_OpenRouter>
AI_MODEL=openai/gpt-oss-120b:free

# Вариант Qwen / Alibaba DashScope:
#   AI_API_BASE_URL=https://dashscope-intl.aliyuncs.com/compatible-mode/v1
#   AI_API_KEY=<ключ_DashScope>
#   AI_MODEL=qwen-plus
```

> AI-поиск **по умолчанию выключен** даже при заданном ключе. Включается
> администратором в интерфейсе FEED (тумблер «Умный поиск» виден только при
> заданном ключе и праве «Управление пользователями»). Ключ хранить только в
> `.env`, в git не коммитить.

## 5. Хранилища (named volumes) — НЕ удалять

Пользовательские файлы лежат в Docker named volumes и переживают пересборку:

| Volume           | Содержимое                                  |
|------------------|---------------------------------------------|
| `postgres_data`  | база данных                                 |
| `tdo_uploads`    | файлы DCC (проектные документы)             |
| `vendor_uploads` | документы подрядчиков (модуль Vendors)      |
| `feed_storage`   | документация FEED                           |
| `minio_data`     | объектное хранилище MinIO                   |

> ⚠️ Не выполняйте `docker compose down -v` — флаг `-v` удаляет volumes
> вместе со всеми файлами и базой. Для остановки используйте
> `docker compose down` (без `-v`).

## 6. Проверка после деплоя

1. Открыть `http://<сервер>:3000`, войти как админ — страница логина грузится,
   вход проходит.
2. **FEED**: загрузить PDF — появляется окно прогресса, документ распознан.
   Повторная загрузка того же файла → «дубль пропущен».
3. **Vendors**: создать приглашение подрядчику.
   - Если SMTP настроен — в модалке зелёная плашка «Письмо отправлено на …»,
     подрядчику приходит письмо со ссылкой; при входе по ссылке приходит код.
   - Ссылка в письме ведёт на `PUBLIC_BASE_URL` (а не на localhost).
4. Логи без ошибок: `docker compose logs backend | tail -50`.

### Диагностика писем

- Письмо не пришло, в модалке «Письмо НЕ отправлено» → проверить `SMTP_*` в
  `.env`, перезапустить backend, посмотреть `docker compose logs backend`
  (там будет причина: неверный логин/порт/TLS).
- Без SMTP код/ссылка пишутся в лог backend (dev-режим) — для прода это не
  годится, SMTP заполнить обязательно.

## 8. Разбор инцидента 2026-06-17 (FEED не грузится, CORS, письма)

### 8.1. `column feed_files.lang does not exist` + «No Access-Control-Allow-Origin»

**Причина.** Раньше схема БД обновлялась только `create_all()` — он создаёт
новые таблицы, но НЕ добавляет новые колонки в уже существующие. После
обновления моделей FEED в таблице `feed_files` на проде не было колонки `lang`
(и др.) → запрос падал с 500. Ответ 500 отдаётся в обход CORS-middleware,
поэтому браузер показывал не настоящую причину, а «No Access-Control-Allow-
Origin» (мнимый CORS).

**Решение.** В код встроена общая авто-миграция при старте backend: при
запуске она сама добавляет недостающие колонки по моделям. Достаточно:

```bash
git pull origin main
docker compose build backend
docker compose up -d
docker compose logs backend | grep -i "auto-migration"   # увидите добавленные колонки
```

Никаких ручных SQL не нужно. Данные не теряются.

### 8.2. Про CORS — заголовок `Access-Control-Allow-Origin`

Его добавляет **backend** (middleware FastAPI), не nginx и не frontend.
В коде уже настроено: разрешены `localhost`, `127.0.0.1` и все приватные сети
(`10.x`, `192.168.x`, `172.16–31.x`) на любом порту через regex. Поэтому
origin `http://192.168.11.237:3000` проходит **даже без** `CORS_ORIGINS`.

> Если всё же задаёте `CORS_ORIGINS` в `.env` — используйте **прямые** кавычки
> ASCII `"`, а не «ёлочки»/«умные» `“ ”` (их подставляет почта/Word). Иначе
> JSON не распарсится. Пример правильно:
> ```
> CORS_ORIGINS=["http://192.168.11.237:3000"]
> ```
> Это объясняет замеченный «разный формат»: `VITE_API_URL` — без кавычек,
> `CORS_ORIGINS` — JSON-массив в прямых кавычках. Так и должно быть.

### 8.3. Письма: `DH_KEY_TOO_SMALL` и `SMTP AUTH not supported`

**Причина.** Корпоративный SMTP использует слабый DH-ключ — стандартный
Python (SECLEVEL=2) его отвергает (`DH_KEY_TOO_SMALL`). При отключённом TLS
сервер не даёт авторизацию (`AUTH not supported`), т.к. AUTH разрешён только
после STARTTLS.

**Решение (в коде).** Backend теперь создаёт SSL-контекст с `SECLEVEL=1` —
слабый ключ принимается; поддержан implicit SSL (порт 465) и STARTTLS (587).
**TLS нужно снова ВКЛЮЧИТЬ:**

```dotenv
SMTP_USE_TLS=true       # вернуть true (после STARTTLS заработает AUTH)
SMTP_PORT=587           # или 465 — тогда implicit SSL
# Если сертификат сервера самоподписанный и появится ошибка проверки:
SMTP_INSECURE=true
```

После правок `.env` — `docker compose up -d` (пересборка не нужна, это runtime-
переменные; но `docker compose up -d` перечитает их). Проверить отправку:
создать приглашение подрядчику → в модалке должна быть зелёная плашка
«Письмо отправлено».

### 8.4. Нельзя удалить старую MR

У MR с приглашениями обычная кнопка удаления скрыта (защита истории
тендера). Для администратора добавлена кнопка **«Занулить MR»** — полное
каскадное удаление MR со всеми приглашениями/ответами/файлами. Видна админу
(право «Управление пользователями») в шапке выбранной MR.
