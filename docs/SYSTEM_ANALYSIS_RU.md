# Часть I. Система ТДО

## 1. Назначение и охват

IvaMaris TDO — система управления технической документацией EPC-проекта
(владелец — заказчик, работают также подрядчики). Три модуля в одном
приложении, переключаются в шапке сайдбара:

| Модуль | Суть | Пользователи |
|---|---|---|
| **DCC** (ядро ТДО) | Реестр MDR → выпуск ревизий → ревью заказчика → CRS → закрытие документа | заказчик + подрядчик |
| **Закупки** (Vendors) | Заявки MR из REQ, чек-листы, приглашения подрядчиков по ссылке+коду | заказчик; подрядчик — гостевой портал |
| **FEED** | Библиотека документации стадии FEED: карточки по шифру, комплектность, поиск, RAG-агент | заказчик (по праву can_access_feed) |

## 2. Архитектура и стек

```
frontend (React 19 + TS + Vite + AntD 5) ──/api/v1──▶ backend (FastAPI + SQLAlchemy)
                                                        ├── PostgreSQL (прод) / SQLite (dev)
                                                        ├── Qdrant (вектора RAG)
                                                        ├── файловые volume'ы (5 шт.)
                                                        └── OpenRouter (LLM, опц.)
```

- **Backend**: ~11.7k строк Python; 11 роутеров, 8 сервисов, 32 таблицы.
  Монолит, синхронный SQLAlchemy, авторизация JWT (access+refresh).
- **Frontend**: 19 страниц, hash-роутинг самописный в `App.tsx`,
  мульти-профильные токены в localStorage (`?profile=` для тестов ролей).
- **Деплой**: docker-compose (db, backend, frontend, qdrant, redis, minio).
- **Миграции**: Alembic НЕТ. `create_all()` + самописная авто-миграция
  колонок при старте (`_ensure_all_model_columns`) — рабочая, но см. риски.
- **Тесты**: 54 файла pytest — хорошее покрытие для проекта такого размера.

## 3. Модель доступа

15 гранулярных прав (`PERMISSION_KEYS` в deps.py), выдаются админом
индивидуально; admin получает всё. Ролевая модель поверх прав:

| Роль | Ключевые права | Функция в процессе |
|---|---|---|
| admin | все | наблюдатель; процессные кнопки в карточке скрыты намеренно |
| Рук. ТДО подрядчика | upload, respond, tdo_queue, mdr | создаёт MDR, модерирует выпуск (очередь ТРМ) |
| Разработчик подрядчика | upload, respond | грузит PDF, отвечает на замечания |
| LR заказчика (лид-ревьюер) | raise, publish, reporting | финальные carry-over решения, публикует CRS |
| R заказчика (ревьюер) | raise, reporting | замечания и рекомендации (не финальные) |

Дополнительно: модульные права `can_access_vendors`, `can_access_feed`
включают целые модули (роутеры закрыты на уровне dependencies).

## 4. Ядро DCC: жизненный цикл документа

Цепочка (7 шагов, линейная с ветвлением на несогласии):

```
MDR (реестр, план сроков)
 → Ревизия A (dev грузит PDF, цель IFR)
 → Очередь ТРМ (рук. ТДО: одобрить → UNDER_REVIEW / отклонить CANCELLED_BY_TDO)
 → Ревью заказчика (LR + R параллельно, замечания к PDF с аннотациями)
 → CRS (LR собирает замечания, публикует подрядчику: OWNER_COMMENTS_SENT)
 → Ответ подрядчика (A — согласен / I — обсуждение)
 → Carry-over (LR: устранено/не устранено) → новая ревизия или закрытие
Финал: ревизия 00 с целью AFD + код AP = документ завершён (uploads locked)
```

Статусная машина ревизий (`REVISION_STATUS_FLOW` в documents.py) задаёт
допустимые переходы — защита от «перепрыгивания» этапов.

**Прогресс документа** — ступени от событий: 70% (выпуск A/IFR) → 75%
(ревью A) → 80% (выпуск B) → 85% (циклы) → 90% (выпуск 00/AFD) → 100% (AP).
Идёт в отчётность (Reporting) и дашборд.

Смежные подсистемы ядра: уведомления (с контекстом проект/документ/ревизия),
аудит-лог, workflow-статусы (справочник, редактируемый), матрица ревью по
проекту, шаблоны шифров (cipher_templates), smart-upload (автораскладка PDF
по иерархии шифра с распознаванием штампа).

## 5. Модуль Закупки (кратко)

- Импорт REQ (.docx) → MR со структурой: теги, Material Summary,
  чек-листы заказчика/подрядчика (mr_owner_items / mr_vendor_items).
- До 5 приглашений подрядчиков на MR; вход по персональной ссылке
  (`#/vendor/<id>?t=<token>`) + email-код (SMTP, STARTTLS c авто-детектом,
  SECLEVEL=1 для слабых DH, SMTP_HELO для Exchange).
- Изоляция подрядчика: гостевой JWT видит только свой MR; audit-лог отдельный.
- Сверка чек-листа с FEED: колонка «FEED» показывает наличие/ревизию
  документа и даёт скачать главный PDF (см. часть II).
- Статусы MR: DRAFT → OPEN → CLOSED → AWARDED; force-delete для админа.

Функционально модуль зрелый; главный внешний риск — зависимость от
корпоративного SMTP (уже отлажено на инцидентах).

# Часть II. Модуль FEED

## 6. Назначение

Библиотека документации стадии FEED: 2086 реальных файлов → **898 карточек
документов**. Карточка = уникальный шифр; внутри — файлы-версии (языки
RU/EN/BI, ревизии, ACRS, редактируемые исходники).

## 7. Модель данных

```
FeedDocument (шифр без ревизии, uniq per project)
 ├─ discipline_code (из шифра: EL, IN, PR, …)
 ├─ doc_class: 1 | 1A          ← 1А требует ACRS
 ├─ latest_rev, issue_purpose, rev_date
 ├─ title_en / title_ru        ← из текста PDF
 ├─ search_text (до 400К)      ← накопленный текст всех языковых версий
 └─ FeedFile[]
     ├─ kind: REVISION | ACRS
     ├─ lang: RU | EN | BI | NA
     ├─ rev, sha256 (дедуп), file_path (volume feed_storage)
     └─ is_master (PDF) / is_editable (dwg/xlsx/docx…) — вычисляемые
```

## 8. Парсер имён файлов — ключевой механизм

Выверен по полному реальному списку (2086 имён, 0 нераспознанных).
Канон: `IMP-FD-UU-SS-DISC-TYPE-SERIAL[суффиксы]`.

| Суффикс | Обработка |
|---|---|
| `-01`/`-02` (2 цифры) | ревизия |
| `-EN/-RU/_EN/_RU/-BI` | язык; версии группируются в ОДНУ карточку |
| `201A/257B` (буква в серийнике) | РАЗНЫЕ документы |
| `-ACRS`, `_ACRS`, `-ACRS-NNN` | kind=ACRS, авто-подъём класса до 1А |
| `-CRS`, `-IR01`, `_1/_2` (листы), `[01]` (копии) | метаданные, отбрасываются |

Фолбэк — распознавание штампа из текста PDF (для файлов без шифра в имени).
Нераспознанные → строка `UNRESOLVED-…`, правится вручную.

**Комплектность** (индикатор «⚠ не хватает»): класс 1 — флаг только если
есть одна языковая версия без второй (одиночный PDF без языка = полный);
класс 1А — нужен PDF + ACRS. Счётчики некомплекта по дисциплинам.

## 9. Загрузка и хранение

- Пофайловая загрузка с прогресс-модалкой (PDF парсится ~3 с).
- Дедуп по sha256: внутри пачки и по проекту (даже под другим именем).
- Извлечение текста: один проход pypdf (до 12 стр.) → и метаданные, и
  search_text; fallback pdftotext.
- Удаление: сначала БД+commit, затем файлы с диска (устойчиво к сбоям ФС).

## 10. Поиск — три контура

1. **По шифру** — прямой ilike по doc_number, работает всегда (частичный,
   любой регистр). Плюс живой фильтр на странице + permalink
   `#/docchecker?doc=ШИФР`.
2. **Keyword** — ilike-предфильтр в БД + casefold-скоринг в Python
   (кириллица-безопасно), сниппеты. Это и фолбэк агента.
3. **RAG-агент** (LangGraph): `embed(bge-m3, локально) → Qdrant top-20 →
   rerank(bge-reranker) top-6 → LLM(OpenRouter) → ответ + источники`.
   Индексация: полная (`POST /feed/agent/reindex`) + инкрементальная в фоне
   при загрузке. Ошибки стека/LLM выводятся в чат с ⚠️, ниже — keyword.
   Вкл/выкл тумблером (SystemSetting), по умолчанию ВЫКЛ.

⚠️ Статус на дату анализа: ключ OpenRouter без кредитов — LLM недоступен
(free-модели закрыты провайдером), агент честно падает в keyword-фолбэк.

## 11. Интеграция с Закупками

`GET /mr/{id}/feed-links`: для каждого пункта чек-листа заказчика ищется
FEED-карточка по нормализованному шифру (язык отрезается так же, как в
парсере FEED). Отдаёт: наличие, последнюю ревизию, mismatch с ревизией REQ,
id главного файла (PDF; приоритет BI→EN→RU). UI: зелёный «в FEED rev N» /
оранжевый конфликт ревизий / серый «нет в FEED».

## 12. Сильные стороны FEED

- Парсер выверен по всему реальному корпусу — группировка карточек точная.
- Дедуп по содержимому, устойчивое удаление, файлы на volume.
- Поиск по шифру гарантированный; RAG-контур деградирует изящно.
- Комплектность и счётчики — реальная операционная ценность для заказчика.

# Часть III. Риски, техдолг, рекомендации

## 13. Сквозные риски (по убыванию важности)

| # | Риск | Деталь | Митигция |
|---|---|---|---|
| 1 | **Нет Alembic** | авто-миграция добавляет колонки, но не переименования/индексы/NOT NULL; расхождение схем dev(SQLite)/prod(PG) уже стреляло | внедрить Alembic, зафиксировать baseline |
| 2 | **documents.py — монолит ~3.3k строк** | вся логика ядра в одном файле; правки рискованны | распил на mdr/revisions/review/crs роутеры |
| 3 | **JWT в localStorage** | XSS = кража токена; для LAN приемлемо, для интернета — нет | httpOnly cookie при выходе в интернет |
| 4 | **RAG-зависимость от OpenRouter** | ключ без кредитов = агент мёртв; free-модели нестабильны | бюджет на ключ ИЛИ локальная LLM (Ollama/vLLM — протокол уже совместим) |
| 5 | **Race condition carry-over** | LR и R одновременно правят решение — перезапись | optimistic-lock (version) на carry_over_decisions |
| 6 | **redis и minio — балласт** | 0 и 1 ссылка в коде; контейнеры крутятся зря | убрать из compose (или запланировать реальное использование) |
| 7 | **SQLite dev vs PG prod** | различия LIKE/регистра уже давали баги поиска | docker-compose.dev с PG |
| 8 | **bge-m3 в backend-процессе** | ~2GB RAM в том же процессе, что API | вынести embed/rerank в отдельный сервис при росте нагрузки |

## 14. Техдолг поменьше

- Hash-роутинг самописный — работает, но растёт вширь (parseHash уже
  ветвится на модули); при усложнении — react-router.
- i18n частичный: Закупки переведены, DCC/FEED — только RU.
- `FeedDocument.search_text` в основной таблице (до 400К на строку) —
  при росте вынести в отдельную таблицу/только в Qdrant.
- antd v5 + React 19 — официально не поддерживаемая пара (warnings в
  консоли), пока работает.
- Прогресс-ступени захардкожены в коде (70/75/80/85/90/100) — вынести в
  справочник, если заказчик захочет менять веса.

## 16. Итоговая оценка

Система функционально зрелая: полный документооборот EPC-цикла, три
рабочих модуля, изоляция подрядчиков, аудит, 54 файла тестов. Основные
проблемы — инфраструктурные (миграции, монолитный роутер, dev/prod-паритет),
а не продуктовые. FEED после выверки парсера по реальному корпусу — самый
надёжный модуль; его единственная хрупкая точка — внешний LLM-провайдер,
и она уже обёрнута фолбэком.
