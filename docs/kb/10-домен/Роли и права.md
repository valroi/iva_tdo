# Роли и права

Две оси: **сторона** (`User.company_type`: contractor / owner / admin) и **роль в проекте**
(`ProjectMember.member_role`), плюс **матрица рассмотрения** (`ReviewMatrixMember`) — она
назначает LR/R по дисциплине конкретного проекта.

## Стороны и кто что делает

| Кто | company_type / member_role | Делает |
|---|---|---|
| Рук. ТДО подрядчика | contractor / `contractor_tdo_lead` | Заводит MDR, отправляет ревизии в ТРМ, грузит файлы |
| Разработчик подрядчика | contractor / `contractor_member` | Создаёт ревизии, грузит PDF и редактируемые, отвечает на замечания |
| LR заказчика | owner + матрица `LR` | Консолидирует замечания, отправляет CRS, ставит AP |
| R заказчика | owner + матрица `R` | Даёт замечания или отмечает «без замечаний» |
| Наблюдатель | любая / `observer` | Видит **всё** read-only, задач и действий нет |
| Админ | admin | Наблюдатель + администрирование; процессных кнопок нет |

## Как устроена матрица назначений

Строка = `(проект, раздел discipline_code, тип doc_type, level, state LR|R, пользователь)`.

- **Адресация — пара «категория + раздел»** (`category` + `discipline_code`). Одна дисциплина
  в разных категориях — разные документы и разные люди: концепции PF с дисциплиной SE и
  отчёты изысканий категории SE рассматривают разные составы.
- **`category IS NULL` — «все категории»**: строки, заведённые до 2026-09-01. Работают как
  раньше, в таблице помечены «все категории». Разделять их — вручную через «Изменить».
- **Раздел «SE» в категории SE покрывает все виды отчётов** (IGDI, IGMI, IEI…) — одна строка,
  если состав общий. Точечно назначить на конкретный вид отчёта тоже можно.
- Единая точка правил — `_matrix_match_clause` (`routers/documents.py`). Через неё идут
  ВСЕ обращения к `ReviewMatrixMember`; продублирована в `services/matrix_gap.has_lead_reviewer`
  (проверка до создания документа) и в подсказках фронта — менять синхронно.
- **`doc_type` не используется в матчинге**: фронт отправляет `doc_type = discipline_code`,
  `level = 1`. Историческое поле.
- **Уникальность строки** — по `(проект, категория, раздел, пользователь, level)`, без учёта
  роли. Одного человека нельзя завести дважды по одной паре: чтобы сменить R↔LR, нужно
  редактировать строку. В Postgres это индекс `uq_review_matrix_member_cat`
  с `COALESCE(category,'')`, создаётся автомиграцией `_ensure_review_matrix_category`.
- **LR по разделу может быть несколько** — уведомления и право отправить CRS получают все.
- Справочник `mark_discipline` может привязывать марку к дисциплине; при расхождении
  назначение отклоняется (`_validate_mark_discipline_mapping`).
- Матчинг документа с матрицей — `_matrix_discipline`/`_matrix_doc_type`
  ([[Вложенные документы]]): у вложенного берутся поля головного документа.

## Важные тонкости

- **Право ≠ роль.** Кнопки гейтятся правами (`permissions.can_upload_files`, `can_raise_comments`,
  `can_publish_comments`, `can_process_tdo_queue`) — см. `frontend/src/utils/revisionActions.ts`.
- **Матрица даёт права сама по себе**: назначение LR/R снимает «глобальный замок»
  (`deps.matrix_permission_grants`) — иначе админ назначал LR, а кнопок у него не было.
- **Наблюдатель** видит ревизии в любом статусе (`_owner_can_access_revision` пропускает observer),
  но в очередь задач не попадает — иначе на Обзоре висел чужой список.
- **AP ставит только LR.** R может лишь рекомендовать (carry-over в режиме `recommendation`).

Связано: [[Жизненный цикл ревизии]], [[CRS и передача замечаний]], [[Уведомления]].

## Что попадает в «Текущие задачи»

Список на «Обзоре» = очередь рассмотрения (`list_owner_review_queue`) + непрочитанные
уведомления. Для стороны заказчика очередь фильтруется **по матрице**: показываются только
документы тех пар «категория + раздел», где человек назначен, с учётом отсечки по дате
(см. ниже). Раньше фильтр был только по проекту — ревьювер, назначенный на один раздел,
видел все документы проекта как свои задачи.

Задача живёт, пока мяч у заказчика: статусы `UNDER_REVIEW` и `CONTRACTOR_REPLY_A`.
В `OWNER_COMMENTS_SENT` / `CONTRACTOR_REPLY_I` ходит подрядчик — у LR/R задачи нет.
Клик по задаче открывает карточку ревизии; очереди ТРМ и CRS — отдельные экраны для
пакетной работы ([[Уведомления]]).

## Назначение задним числом

Отсечка работает только по **закрытым** рассмотрениям. Пока ревизия в статусе
`UNDER_REVIEW`, состав не зафиксирован: добавленный сегодня ревьювер обязан участвовать в
текущем круге. Как только LR отправил CRS (`LR_SENT_TO_CONTRACTOR`) или выставил AP
(`AP_SET`), состав считается закрытым, и назначенные позже по этой ревизии не ожидаются —
работать они начинают со следующего круга. Иначе новый человек мгновенно повисал в статусе
«рассматривает» на всех старых и уже отработанных ревизиях (`_review_closed_at`).

Права на действия (`_is_lr_for_document`, `_owner_matrix_role_for_document`) отсечкой НЕ
ограничены — если новому LR нужно вмешаться в старую ревизию, он может. Если под отсечку
не попал никто (матрицу заполнили уже после отправки), показывается полный состав.

## Пустая матрица

Документ по разделу без назначенного LR создать нельзя — ни через форму, ни импортом
(`_ensure_reviewers_assigned`). Подрядчик видит объяснение прямо в форме, как только выбрал
раздел; администраторы и адресаты из настройки `matrix_gap_notify_emails` получают
уведомление с письмом. Админ проверкой не ограничен. Если по разделу назначений нет у уже
существующего документа, рассылка уходит этим же получателям, а не всем сотрудникам
заказчика ([[Уведомления]]).
