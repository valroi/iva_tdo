# CRS и передача замечаний

**CRS** — пакет замечаний, который LR отправляет подрядчику. Ключевое правило:

> Замечания заказчика на этапе рассмотрения — **внутренние**. Подрядчик не видит их и не получает
> уведомлений, пока LR не отправит CRS.

## Как реализовано

- Флаг `Comment.is_published_to_contractor` — переключается **только** в `crs-send`
  (`POST /comments/crs-send`) и при автоматическом AP-без-замечаний.
- Все выдачи замечаний подрядчику фильтруются по этому флагу: `list_comments`,
  `get_revision_card`. Аннотатор PDF рисует оверлеи только из отфильтрованных данных.
- Уведомление о новом замечании уходит **только LR** (не создателю документа).
  Раньше в получателях был `document.created_by_id` — замечания «падали» подрядчику сразу
  (исправлено 2026-08-05, коммит `cb62207`).

## Что происходит при отправке CRS

1. Замечаниям проставляется `crs_number` (`{ПРОЕКТ}-{ОТПР}-{ПОЛУЧ}-CRS-00001`) и `crs_sent_at`.
2. Ревизия → `OWNER_COMMENTS_SENT`, дедлайн подрядчику по SLA.
3. Подрядчику уходит `OWNER_COMMENTS_PUBLISHED`.
4. Гасятся задачи заказчика по этой ревизии: `TDO_SENT_TO_OWNER`, `REVIEW_DEADLINE_SOON`,
   `R_NO_COMMENTS`, комментарные события — см. [[Уведомления]].

## Коды замечаний

`RJ` (ревизия не засчитывается) > `CO` (существенные) > `AN` (незначительные) > `AP` (согласовано).
Эффективный код ревизии = явный `Revision.review_code`, иначе «худший» из опубликованных
родительских замечаний. Логика продублирована на фронте (`utils/revisionProcess.ts`) и бэке
(`_latest_effective_review_code` в `mdr.py`) — при правке менять обе.
