# Уведомления и задачи

Одна таблица `notifications` кормит и **Обзор** («Текущие задачи» = непрочитанные), и страницу
**Уведомления** (вкладки «Активные» / «Отработано»). Плюс задачи-очереди у заказчика
(`/revisions/owner-review-queue`) — это не уведомления, а вычисляемый список.

## Типы событий (главные)

| event_type | Кому | Когда |
|---|---|---|
| `NEW_REVISION_FOR_TDO`, `REVISION_UPLOADED_FOR_TDO` | рук. ТДО подрядчика | создана ревизия / загружен PDF |
| `TDO_SENT_TO_OWNER` | LR и R по матрице | ревизия отправлена в ТРМ |
| `OWNER_COMMENT_CREATED` | **только LR** | R/LR создал замечание (подрядчику НЕ уходит) |
| `OWNER_COMMENTS_PUBLISHED` | подрядчик | LR отправил CRS |
| `REVIEW_DEADLINE_SOON` | ревьювер | ≤1 дня до дедлайна, задача открыта |
| `DOC_OVERDUE_PLAN_START` | рук. ТДО подрядчика | просрочка планового старта (не админу) |

Все уведомления **дублируются на e-mail** хуком `after_commit` (`services/notification_email.py`).

## Группировка (антиспам)

Подрядчику по ревизии держим **одно** непрочитанное уведомление-сводку
(`_upsert_crs_notification`): при поштучной публикации замечаний текст
обновляется, а не создаётся новое уведомление. Письма уходят только на новые
`Notification` (`session.new`), поэтому подрядчик получает **одно письмо на
пакет**, а не на каждое замечание.

Текст сводки: «CRS <номер>: <документ>, ревизия A — замечаний: 3, итоговый код: CO».
Итоговый код — худший из опубликованных (RJ > CO > AN > AP), считает
`_revision_remarks_digest`. Применено во всех трёх точках: массовая отправка CRS,
поштучная публикация, автоматический AP.

## Гашение (главное правило)

Уведомление должно исчезать, когда действие выполнено. Точки гашения:

- действие ревьювера (замечание / «без замечаний») → его `TDO_SENT_TO_OWNER`, `REVIEW_DEADLINE_SOON`;
- отправка CRS → задачи заказчика по ревизии;
- загрузка PDF / отправка в ТРМ → задачи подрядчика;
- **автоочистка при чтении списка** (`_cleanup_stale_notifications` в `routers/notifications.py`):
  гасит уведомления по не-последней ревизии, по завершённым документам (AFD+AP), просрочки при
  наличии ревизии и дубли. Работает для всех ролей и подчищает уже накопленный мусор.

Связано: [[CRS и передача замечаний]], [[Идемпотентность и дубли]], [[Жизненный цикл ревизии]].

## Переход из «Обзора»

Кнопка «Открыть» в задаче ведёт в карточку ревизии, если у уведомления есть `revision_id`
(есть у всех задач, кроме просрочек старта). Очереди — «Очередь ТРМ», «CRS» — открываются
только как запасной путь, когда ревизия неизвестна: раньше заказчика по любой задаче уводило
в очередь ТРМ и документ приходилось искать глазами.

## Почта: одно письмо в конце дня

Мгновенно письмо уходит только по срочным событиям — `INSTANT_EVENT_TYPES` в
`services/notification_email`: CRS подрядчику (`OWNER_COMMENTS_PUBLISHED`, с него идёт срок
ответа) и заявка на регистрацию. Всё остальное копится и в **18:00 МСК** уходит одним письмом
на пользователя, сгруппированным по документам (`services/daily_digest`, демон-поток как у
напоминаний о дедлайнах).

Отметка об отправке — `Notification.email_sent_at`: по одному уведомлению письмо уходит ровно
один раз, повторный прогон дайджеста ничего не дублирует. Прочитанные в интерфейсе уведомления
в сводку не попадают. Добавляя новый тип события, реши: срочный он (в `INSTANT_EVENT_TYPES`)
или дайджестовый — и добавь человекочитаемый заголовок в `_EVENT_TITLES`.
